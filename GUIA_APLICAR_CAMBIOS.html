Siete cargas a GitHub

Cómo aplicar los cambios de la carpeta actualizacion-real. Todo se hace arrastrando archivos en el navegador: no hay que instalar nada ni escribir comandos. Unos 15 minutos.

Lo primero, para que no te asustes a la mitad

Las primeras cinco cargas van a marcar ✗ rojo en GitHub. Es correcto y esperado: el código nuevo ya está arriba, pero la base de datos todavía es la vieja, y la validación no deja publicar datos que no cuadran. La carga 6 es la que pone todo en verde, porque es la que trae la base corregida.

Mientras eso pasa, el tablero publicado no se rompe: sigue mostrando el cierre anterior. Eso es a propósito.

Por qué el orden no se puede cambiar

El código nuevo entiende una base con columnas vacías y hojas sin capturar. El código viejo no: exige que todo traiga número. Y la base nueva tiene columnas vacías a propósito, porque hay módulos que todavía no se capturan.

Si subes…Con…Resultado
la base primeroel código viejo La validación la rechaza. No publica.
el código primerola base vieja ✗ rojo, y está bien. El tablero conserva el cierre anterior.
la base al finalel código nuevo ✓ verde. Publica.

Por eso las carpetas se llaman para-1-etl, para-2-… y así: el número es el orden de carga, y el nombre es la carpeta de destino en GitHub.

Las dos reglas que evitan el desastre

  1. Arrastra los ARCHIVOS, no la carpeta. Abre para-1-etl, selecciona los archivos de adentro (Ctrl+A) y arrastra esos. Si arrastras la carpeta cerrada, GitHub crea una subcarpeta con ese nombre y los archivos quedan en el lugar equivocado.
  2. Antes de confirmar, lee la ruta que aparece arriba de la zona de arrastre. Debe decir exactamente la carpeta de destino de esa carga. Es la única verificación que impide que un archivo aterrice donde no va.

Y una que ya nos costó una vez

No uses choose your files para navegar entrando a carpetas. Al hacerlo, GitHub sube el contenido aplanado: todos los archivos juntos en un solo nivel, y el repositorio deja de funcionar. Arrastrar es lo seguro.

La pantalla que vas a ver siete veces

Cada carga de aquí en adelante te da tres cosas: el enlace directo (no tienes que buscar nada en el menú), los archivos que van, y el mensaje del commit para copiar y pegar.

De cada hoja solo son obligatorias sus llaves —periodo, unidad, área— y la magnitud base. Todo el detalle es opcional y puede quedar vacío. Y en plantilla faltan las áreas y unidades que no se capturaron: Mina Realito no tiene ninguna fila en los 13 meses.

Antes de cargar la primera nómina real: repositorio privado

El repositorio es público. La plantilla agregada que vas a subir ya estaba en el historial, así que esta carga no expone nada nuevo. La nómina es otra cosa: en el momento en que se cargue, el costo laboral por unidad queda visible para cualquiera en internet, y el historial de git lo conserva aunque después borres el archivo.

Hacerlo privado después no alcanza. Hay que crear un repositorio nuevo privado —plan GitHub Team o superior— y publicar ahí. Es el paso que conviene dar antes de capturar nómina, no después. Pídeme el paso a paso cuando quieras y lo armamos.
